# Prism — 저지연 원격 데스크톱 (게임 스트리밍급)

## Context

`/Users/aodjo/Documents/prism`은 현재 완전히 빈 디렉토리다. 목표는 **게임 플레이가 가능한 수준의 저지연**과 **간단한 설치**를 동시에 만족하는 원격 데스크톱 "Prism"을 처음부터 만드는 것.

확정된 요구사항:

| 항목 | 결정 |
|---|---|
| 호스트 OS | Windows + macOS + Linux (전부) |
| 클라이언트 | 네이티브 전용 |
| 네트워크 | 처음부터 인터넷 경유 (NAT 트래버설 포함) |
| UI 셸 | TypeScript / Electron |
| 네이티브 코어 | **Rust** → `napi-rs`로 Node 애드온화 |
| 코덱 계층 | 네이티브 SDK 직접 호출 (NVENC/AMF/oneVPL/VideoToolbox/VAAPI) |
| 1차 목표 스펙 | 1440p120, HEVC·AV1까지 |

보유 장비: 이 Mac(Apple Silicon, macOS 26.6) + NVIDIA GPU Windows PC + AMD/Intel 내장 GPU Windows PC + Linux 박스. 이 Mac에는 Node 24 · Python 3.14 · ffmpeg 9가 있고 **Rust 툴체인은 아직 없다** (M0에서 `rustup` 설치).

**성공 기준(측정 가능한 정의):** LAN에서 캡처→표시(glass-to-glass) 추가 지연 **p99 < 25ms @ 1440p120**, 인터넷에서 **< 25ms + RTT**. Moonlight/Parsec와 동급 목표치이며, 이 문서의 모든 설계 결정은 이 숫자에서 역산됐다.

## 이 프로젝트를 성립시키는 단 하나의 규칙

> **비디오 프레임은 절대 V8(JavaScript)을 통과하지 않는다.**

Electron/TS를 쓰면서 게임 지연을 달성하는 방법은 이것 하나다. 데이터 평면과 제어 평면을 물리적으로 분리한다:

- **제어 평면 (TypeScript/Electron):** 페어링 UI, 시그널링, 세션 협상, 설정, 코덱 네고 정책, 비트레이트 정책, 통계 표시, 업데이터
- **데이터 평면 (Rust):** 캡처 → 인코딩 → 패킷화 → 송신 → 수신 → 디코딩 → 표시 → 입력. 전용 스레드에서 끝까지 처리하며 JS 이벤트 루프를 한 번도 건드리지 않는다.

napi-rs 표면은 **제어 호출과 통계만** 노출한다. 통계는 `ThreadsafeFunction`으로 **최대 10Hz**. 프레임 버퍼·텍스처·패킷은 절대 넘기지 않는다. napi-rs가 TS 타입 정의(`index.d.ts`)를 자동 생성하므로 제어 평면과 코어의 계약이 컴파일 타임에 맞춰진다.

Node-API 바이너리는 런타임 독립적이라 **`.node` 하나가 Node와 Electron에서 재빌드 없이 그대로 로드**된다.

## 왜 Rust인가 (C++ 대비)

| 항목 | 효과 |
|---|---|
| **Cargo** | CMake + cmake-js + vcpkg × 3 OS 조합이 사라진다. 원래 계획에서 가장 큰 숨은 비용이었고, M0·M8·M10이 실질적으로 몇 주 줄어든다 |
| **napi-rs** | Windows/Linux/macOS 프리빌트 CI/CD 기본 제공. SWC·Rolldown이 쓰는 플랫폼별 optional dependency 패턴 그대로 사용 |
| **windows-rs** | Microsoft가 직접 관리하는 WinRT 프로젝션. `Windows.Graphics.Capture` + D3D11이 C++/WinRT보다 깔끔 |
| **objc2 프레임워크 크레이트** | `objc2-screen-capture-kit`, `objc2-video-toolbox`가 Xcode SDK에서 생성되고 Xcode 릴리스에 맞춰 갱신 |
| **`Send`/`Sync`** | 5개 스레드가 프레임 버퍼·통계를 공유하는 파이프라인에서 실제 버그를 잡는다 |
| **순수 Rust 대체** | Noise→`snow`, FEC→`reed-solomon-erasure`, PAKE→`spake2`, AES-GCM→`aes-gcm`. C 의존성이 코덱 SDK·opus·SDL3로만 줄어든다 |

**유일한 마찰: AMF(AMD 인코더).** COM 유사 vtable이라 bindgen이 깔끔히 못 뽑는다. `amf-shim` 크레이트에 ~200줄 C 심을 두고 `cc`로 빌드한다. 나머지 4개 인코더는 문제없다. 부수적으로 Sunshine/Moonlight/OBS 참조 구현이 전부 C++이라 복사가 아닌 번역이 된다.

### 호스트 스레드 모델 (세션당)

| 스레드 | 역할 |
|---|---|
| T1 | 캡처 (OS 콜백 스레드) → GPU 텍스처 핸들을 인코더로 직접 전달 |
| T2 | 인코드 서브밋 (GPU 디바이스 소유) |
| T3 | 인코드 완료 대기(async 이벤트) → **슬라이스 단위** 패킷화 → FEC → 페이싱 송신 |
| T4 | 네트워크 수신 — 입력 이벤트, ACK, 피드백 |
| T5 | 오디오 캡처 → Opus → 송신 |

**제로카피 필수:** 캡처된 GPU 텍스처가 CPU로 내려오지 않고 그대로 인코더 입력이 된다. Windows는 `ID3D11Texture2D` → `NvEncRegisterResource`, macOS는 `IOSurface` → VideoToolbox, Linux는 DMA-BUF → VAAPI.

### 클라이언트 스레드 모델

| 스레드 | 역할 |
|---|---|
| T1 | 네트워크 수신 → 재조립 → FEC 복구 → 디코드 서브밋 |
| T2 | 디코드 완료 → 표시 큐 |
| T3 | 표시 (vblank / CVDisplayLink 구동, 적응형 페이싱) |
| T4 | 입력 캡처 → **즉시** 송신 (배칭·페이싱 금지) |

### 클라이언트 창

Electron은 **UI 셸(설정·페어링·호스트 목록)만** 담당한다. 스트림 화면은 **Rust가 SDL3로 만든 별도 네이티브 창**에서 렌더링한다. Chromium 컴포지터를 완전히 우회해야 하기 때문이다(컴포지터는 1~2프레임을 먹는다). SDL3가 창 관리 + 상대 마우스 캡처 + 게임패드 + 오디오 출력을 한 번에 해결하고, 렌더러는 플랫폼별 백엔드(D3D11 flip-model / Metal / Vulkan)를 직접 붙인다.

## 지연을 만드는(혹은 죽이는) 12가지 결정

네이티브 SDK를 직접 호출하기로 한 이유가 바로 아래 항목들이다. ffmpeg 추상화로는 1~5번을 제대로 제어할 수 없다.

1. **인코더가 버퍼링하지 못하게 한다 — 가장 중요.**
   NVENC: `outputDelay=0`, B-프레임 0, lookahead 0, `NV_ENC_PARAMS_RC_CBR`,
   **`vbvBufferSize = averageBitRate / frameRate` (딱 1프레임)**, `vbvInitialDelay` 동일.
   VBV가 크면 인코더가 거대한 프레임을 뱉고 전송에 3프레임이 걸린다. 지연 스파이크의 최대 원인.

2. **슬라이스 단위 스트리밍.** `sliceMode=3, sliceModeData=4`(프레임당 4슬라이스). `NV_ENC_LOCK_BITSTREAM`의 슬라이스 오프셋을 읽어 완성되는 즉시 송신. 프레임 시간의 절반가량을 절약한다.

   > **측정 결과 제약:** Apple Silicon 하드웨어 H.264 인코더는 `kVTCompressionPropertyKey_MaxH264SliceBytes`를
   > 지원하지 않는다 (`kVTPropertyNotSupportedErr`, -12900). 따라서 **macOS 호스트에서는 이 항목을 적용할 수 없고**,
   > 프레임이 통째로 인코딩될 때까지 전송을 시작하지 못해 약 반 프레임(1440p120 기준 ~4ms)을 손해본다.
   > 주 목표 경로인 Windows/NVENC 호스트는 슬라이싱을 지원하므로 영향이 없다.
   > 코드에서는 세션을 실패시키지 않고 `VideoToolboxEncoder::slicing_supported()`로 능력을 노출한다.

3. **Async 인코드 + 이벤트 핸들.** `enableEncodeAsync=1` + 완료 이벤트 대기. 폴링 금지.

4. **IDR 대신 intra-refresh.** `enableIntraRefresh=1`, `intraRefreshPeriod=framerate`, `intraRefreshCnt=framerate/4`. 키프레임 비트레이트 스파이크를 없앤다.

5. **LTR + 참조 무효화로 손실 복구.** 클라이언트가 수신 프레임을 ACK → 손실 발생 시 호스트가 `NvEncInvalidateRefFrames` 호출 후 마지막 ACK된 LTR을 참조해 인코딩. **IDR 히칭이 영구히 사라진다.** 좋은 게임 스트리밍과 그저 그런 것의 차이가 여기서 갈린다.

6. **송신 페이싱.** 프레임 패킷을 회선 속도로 몰아 쏘지 않고 프레임 간격의 ~80%에 걸쳐 분산. 버퍼블로트와 버스트 손실 방지.

7. **클라이언트 표시 페이싱.** 디코드 즉시 표시하면 저더, 2프레임 버퍼링하면 +16ms. 측정된 p99 지터로 구동되는 **적응형 큐**(최소 0)를 쓴다.

8. **커서는 클라이언트가 그린다.** WGC `IsCursorCaptureEnabled=false`로 호스트 캡처에서 커서를 빼고, 커서 모양·위치는 제어 채널로 보내 클라이언트가 네이티브 주사율로 직접 렌더링. **체감 지연에서 가장 큰 단일 승리** — 영상이 30ms 늦어도 커서는 즉각 반응한다.

9. **입력 경로는 모든 것을 우회한다.** 페이싱·배칭 없이 즉시 송신, 호스트에서 전용 고우선순위 스레드로 주입. 마우스는 1000Hz 폴링.

10. **클럭 동기화.** 주기적 핑퐁의 min-RTT 샘플로 오프셋 추정. 단방향 지연 측정(혼잡 제어)과 통계 HUD의 전제 조건.

11. **혼잡 제어는 대역폭보다 지연을 우선한다.** 단방향 지연 기울기 + 손실률 기반 AIMD. 지연이 오르면 공격적으로 백오프 — 게임에서는 화질보다 지연이 먼저다.

12. **표시 시점.** D3D11은 flip-model + waitable object + `ALLOW_TEARING`, macOS는 CVDisplayLink. 렌더 어헤드 0.

## 프로토콜

UDP 단일 플로우. ICE로 뚫고, Noise_IK 핸드셰이크로 키 교환 후 ChaCha20-Poly1305로 패킷 단위 봉인.
**구현 완료** — 자세한 레이아웃과 근거는 `docs/wire-format.md`.

```
[1B 채널][... 암호화된 페이로드]
채널: 0=제어  1=비디오  2=오디오  3=입력  4=피드백/ACK
```

비디오 패킷 헤더:
```
frame_id u32 | slice_id u16 | pkt_idx u16 | pkt_count u16 |
flags u8 (idr / last-of-frame / ltr) | capture_ts_us u64 | payload
```
봉인된 데이터그램이 **1200바이트 이하**여야 하므로(PMTU 안전), 평문 예산은 봉인 오버헤드
24바이트를 뺀 **1176바이트**다. 비디오·패리티 페이로드는 여기서 헤더 20바이트를 더 뺀 1156바이트.

- **FEC:** 프레임/슬라이스 단위 Reed-Solomon (`reed-solomon-erasure`). 측정 손실률에 따라 패리티 비율 적응(기본 10~20%).
- **보안:** 장기 신원은 **X25519 키쌍** 하나(최초 실행 시 생성, `~/.prism/identity.key`에 0600으로 보관).
  Ed25519가 아니라 X25519인 이유는 Noise가 쓰는 키가 그것이고, 키를 하나로 두면 "페어링이 고정한
  키"와 "핸드셰이크가 증명하는 키"가 같은 대상이 되기 때문 — WireGuard와 같은 선택.
  세션은 **Noise_IK** 1-RTT + 전방 비밀성. 페어링은 호스트가 표시한 6자리 코드를 **SPAKE2**로
  처리해 공개키를 상호 고정한다 — 코드는 **1회용**이고, 온라인 추측 1번이면 소진된다.
  랑데부 서버는 암호화된 블롭과 ICE 후보만 본다.
- **코덱 네고:** 호스트가 인코딩 가능 목록, 클라이언트가 디코딩 가능 목록을 광고 → 상호 최선 선택. **H.264는 항상 폴백으로 보장.** (AV1 인코딩은 NVIDIA Ada / AMD RDNA3 / Intel Arc 이상에서만 가능하므로 반드시 협상 대상.)

### NAT 트래버설 / 시그널링

**서버는 자체 호스팅한다.** `crates/prism-rendezvous` 바이너리 하나를 저렴한 VPS에 올리고, 그것이
페어링·시그널링·주소 발견·릴레이 폴백을 모두 담당한다. Cloudflare 의존은 없다.

> **별도 STUN 서버가 필요 없다.** 피어가 랑데부 서버로 UDP 패킷을 보내면 서버는 출발지 IP:포트를
> 그대로 관측한다 — STUN이 하는 일이 정확히 그것이다. 시그널링 서버가 UDP를 받으면 STUN 기능은 공짜로 따라온다.
> (Cloudflare Workers는 임의 UDP를 받을 수 없어서 이 통합이 불가능했고, 그것이 자체 호스팅을 택한 이유 중 하나다.)

- **ICE:** `webrtc-ice`를 Rust 코어에 내장. 미디어+입력 플로우는 코어가 자체 ICE 세션으로 소유한다.
- **랑데부 서버:** 호스트가 TLS로 상주 연결을 유지하고, 클라이언트가 호스트 ID로 접속을 요청하면
  서버가 양쪽의 관측된 공인 주소와 ICE 후보를 교환시킨다. 서버는 암호화된 블롭만 보고 키는 절대 못 본다.
- **릴레이 폴백:** 같은 바이너리 안의 UDP 릴레이. 세션 토큰으로 패킷을 양방향 전달만 한다.

#### 릴레이를 쓰지 않는 것이 최우선이다

릴레이는 예외 경로다. 직결 성공률을 올리는 수단을 먼저 갖춘다:

- **UPnP / NAT-PMP / PCP 포트 매핑** — 호스트가 공유기에 포트를 열어달라고 요청한다. 집 게임 PC 시나리오에
  가장 효과적이며 Moonlight이 쓰는 방식이다.
- **IPv6** — 양쪽 다 v6면 NAT 자체가 없다. 후보 수집에서 v6를 우선한다.
- **수동 포트포워딩** 안내를 설정 UI에 둔다.
- 제대로 된 ICE 후보 수집과 홀펀칭.

이것들을 갖추면 릴레이가 필요한 경우는 양쪽 다 대칭 NAT/CGNAT일 때(예: 휴대폰 테더링) 정도로 줄어든다.
앱 UI에는 릴레이 사용 중임을 반드시 표시한다.

#### 비용

| 방식 | 월 비용 | 40Mbps 기준 중계 가능 시간 |
|---|---|---|
| 자체 VPS (예: Hetzner CX22급, 20TB 포함) | **~€4 정액** | ~1,100시간 |
| Cloudflare TURN | 1TB 무료 후 $0.05/GB | 무료분 ~55시간, 이후 시간당 ~$0.90 |

정액제라 사용량이 늘어도 비용이 폭발하지 않는다. 대가는 단일 리전(먼 지역은 릴레이 시 RTT 증가)과
직접 운영이며, 릴레이가 예외 경로인 이상 감수할 만하다.

**시그널링·STUN 트래픽 자체는 무시해도 되는 수준이다.** 주소 발견 교환은 세션당 수백 바이트라,
비용이 발생하는 것은 릴레이된 미디어뿐이다.

### 코덱 협상과 HEVC, 그리고 "절반의 비트레이트"를 실제로 재보니 (2026-09-07)

**협상은 핸드셰이크 안에 태웠다.** Noise 핸드셰이크는 이미 양방향으로 페이로드를 나르고 이미
1 RTT를 쓴다. 따로 협상하면 모든 연결 앞에 두 번째 왕복이 생긴다 — 20바이트를 옮기려고.
클라이언트의 능력이 세션을 여는 메시지에 실려 가고, 호스트의 결정이 세션을 완성하는 메시지로
돌아온다. 세션이 살아 있는 시점에는 이미 설정이 끝나 있다.

**결정은 호스트가 한다.** 한쪽은 해야 하고, 인코딩할 쪽이 자기 하드웨어가 뭘 받아들이는지 안다.
AV1을 요청하고 H.264를 받은 클라이언트는 논쟁이 아니라 동작하는 세션을 갖는다.

이 때문에 `Responder::accept`가 값이 아니라 **콜백**을 받게 바뀌었다. 무엇을 답할지는 상대가 무엇을
물었는지에 달렸는데, Noise 메시지는 한 번만 읽을 수 있다.

**VideoToolbox HEVC를 붙였다.** NAL 파싱이 H.264 전용이었던 게 실제 버그로 드러났다 — 타입이
H.264는 하위 5비트, HEVC는 1~6비트이고, 파라미터 세트가 2개가 아니라 3개(VPS 추가)다. 처음 뽑은
HEVC 파일은 ffprobe가 "Invalid data"로 거부했다. 고친 뒤 **180/180 프레임, Main 프로파일**로 읽힌다.

**그리고 "HEVC는 비트레이트가 절반"을 실제로 쟀다.** 같은 소스(120프레임 720p60), 원본을 raw NV12로
덤프해서 각 디코드 결과와 SSIM 비교:

| 요청 | H.264 실제 / SSIM | HEVC 실제 / SSIM |
|---|---|---|
| 4 Mbps | 4.09 / **0.9644** | 4.10 / **0.9857** |
| 6 Mbps | 6.16 / 0.9960 | 6.10 / 0.9911 |
| 8 Mbps | 7.82 / 0.9980 | 8.16 / 0.9952 |
| 10 Mbps | 9.42 / 0.9990 | 10.23 / 0.9953 |
| 12 Mbps | **9.90** / 0.9992 | 12.30 / 0.9959 |
| 16 Mbps | **10.77** / 0.9994 | 15.07 / 0.9971 |

**통념과 다르다.** HEVC가 분명히 이기는 건 **4 Mbps뿐**이고, 6 Mbps 이상에서는 H.264의 SSIM이
더 높다. Apple의 HEVC 인코더는 0.995~0.997에서 평평해지는 반면 H.264는 0.9994까지 계속 올라간다.
그리고 H.264는 10 Mbps 근처에서 **주는 비트레이트를 다 쓰지 않는다**(16 요청에 10.77 실제).

세 가지 단서를 함께 읽어야 한다:

- **이 소스는 데스크톱이 아니다.** 고주파 바와 그라디언트로 된 합성 패턴이고, 변환 코덱에게
  병리적인 최악의 경우다. 실제 데스크톱(대부분 정지, 텍스트, 가끔 영상)과 다르게 거동한다.
  캡처 경로를 프로브에 물릴 수 있게 되면 다시 재야 한다.
- **SSIM은 지각 품질의 완전한 대리물이 아니다.** HEVC 인코더는 보통 지각 지표로 튜닝되고
  SSIM은 그 선택을 벌한다.
- **그래도 결론은 협상을 지지한다.** 인터넷 경로에서 실제로 쓰는 대역(수 Mbps)이 정확히 HEVC가
  이기는 구간이고, 그게 코덱을 세션마다 고르는 이유다. 하드코딩했다면 어느 쪽을 골랐든 절반의
  경우에 틀렸을 것이다.

### 릴레이 폴백, 그리고 실제 3머신 검증 (2026-09-07)

홀펀칭은 한쪽 라우터라도 목적지와 무관한 매핑을 주면 성공한다 — 대부분이 그렇다. 실패하는 건
**양쪽 다 대칭 NAT**일 때(CGNAT, 휴대폰 테더링). 그 경우엔 펀칭할 주소 자체가 없고, 남는 방법은
양쪽이 닿을 수 있는 기계가 바이트를 넘겨주는 것뿐이다.

**별도 포트를 쓴다(47301).** 시그널링과 릴레이 트래픽이 같은 포트로 오면 서버가 둘을 **추측**해야
하는데, 봉인된 패킷은 설계상 아무것도 아닌 것처럼 보인다. 시그널링 메시지로 파싱돼 버리는 비디오
패킷은 전달되지 않고 삼켜진다. 포트를 나누면 질문 자체가 사라진다: 거기 오는 건 전부 트래픽이고,
아닌 건 8바이트 토큰 하나뿐이다 (봉인 최소 길이 24바이트 < 토큰 8바이트라 절대 헷갈리지 않는다).

**서버는 들여다보지 않는다.** 헤더도 안 붙이고, 길이도 안 바꾸고, 그대로 넘긴다. 릴레이된 세션과
직결 세션은 바이트 단위로 같은 세션이다.

**첫 실행이 버그를 잡았다.** 양쪽이 각자 "직결이 안 된다"를 발견하고 각자 릴레이를 요청하는데,
서버가 요청마다 새 토큰을 만들었다. 두 피어가 서로 다른 토큰으로 릴레이 포트에서 오지 않을 상대를
기다렸고, **아무 데서도 이유를 말하지 않았다.** 같은 (host, client) 쌍에는 같은 토큰을 주도록 고쳤다.

**두 번째 버그도 같은 실행이 잡았다.** CLI 호스트가 core의 세션 열기를 쓰지 않고 자기 복사본을
갖고 있어서, 릴레이 폴백이 CLI에는 아예 없었다. 구현을 하나로 합쳤고, 합치고 나니 이번엔 CLI가
리턴 패스를 **두 번** 켜고 있었다("the return path is already running"). 같은 일을 두 군데서 하면
갈라진다는 걸 한 실행에서 두 번 확인한 셈.

실측 (galbook 호스트·클라이언트, 별도 VM의 랑데부, 같은 LAN):

| 경로 | p50 | p99 | 프레임 |
|---|---|---|---|
| 직결 (랑데부가 소개) | 0.18 ms | 0.39 ms | 300/300 |
| 릴레이 경유 | 0.72 ms | 1.24 ms | 300/300 |

한 홉이 두 홉이 되며 약 0.5 ms. 실제 배포에서는 서버까지의 RTT가 그대로 더해지므로, 릴레이는
예외 경로이고 UI가 사용 중임을 표시해야 한다 — 화면이 무겁게 느껴지는 사람은 그 답이 인코더가
아니라 경로라는 걸 알 자격이 있다.

**서버 배포:** 순수 Rust라 musl 정적 링크가 되고, macOS에서 크로스 빌드한 **1.2 MB 바이너리**
하나를 올려 root 없이(비특권 포트) 돌린다. Docker 이미지는 1.5 MB.

**아직 검증되지 않은 것은 여전히 실제 두 NAT 사이의 홀펀칭이다.** 프로토콜·소개·릴레이는 실제
세 머신에서 확인했지만, 공인 주소를 가진 랑데부가 생기기 전까지 대칭 NAT 판정은 못 한다.

### 오디오 (M7): 소리에는 소리의 경로가 있다 (2026-09-07)

비디오 경로를 재사용하지 **않았다.** 오디오 패킷은 작고, 프레임은 16ms가 아니라 5ms고, 잃은
프레임은 복구가 아니라 은폐한다. 재조립·패리티·표시 페이싱을 공유하면 그 결정 전부가 오디오에는
틀린 결정이 된다.

**그림이 한 프레임 늦는 건 안 보이지만, 소리의 구멍은 들린다.** 그래서 오디오는 자체 지터 버퍼를
갖고, 그림은 소리를 기다리지 않는다. 둘은 **같은 호스트 클럭**을 실어서, 필요한 지점(사람이 말하는
걸 보는 순간)에서만 다시 합쳐진다 — 모든 곳에서 묶으면 둘 중 나쁜 쪽 동작을 양쪽 다 갖게 된다.

**코덱은 순수 Rust Opus.** C 레퍼런스를 쓰면 타깃마다 크로스 툴체인이 필요해지고, 이 크레이트의
다른 모든 의존성은 순수 Rust다. 선택은 측정으로 확정했다 — 48kHz 스테레오, 128 kbps:

| 프레임 | 파형 SNR | 대역 에너지 오차 | 인코드+디코드 | 프레임 길이 대비 |
|---|---|---|---|---|
| 2.5 ms | 26.4 dB | 7.80 dB | 44.2 us | 1.8% |
| **5 ms** | **36.0 dB** | **4.67 dB** | **23.9 us** | **0.5%** |
| 10 ms | 36.5 dB | 1.61 dB | 42.9 us | 0.4% |

5ms가 곡선이 꺾이는 지점. 2.5ms는 같은 소리에 거의 두 배의 처리 비용을 내고 스펙트럼은 더 나쁘고,
10ms는 아무도 알아채지 못할 코덱 개선을 위해 5ms의 지연을 더 낸다.

**첫 측정은 내가 틀렸다.** SNR 0.5 dB가 나왔는데, Opus는 파형을 보존하지 않고(CELT의 PVQ는 대역
에너지만 보존) 게다가 2.5ms의 알고리즘 지연이 있어서 프레임 N 입력과 프레임 N 출력을 비교하면
정렬 자체가 어긋난다. 상호상관으로 지연을 찾아 정렬한 뒤에야 숫자가 말이 됐다.

설계에서 값을 치른 지점들:

- **패리티 없음.** Opus는 자체 대역 내 중복성을 갖고, 디코더는 앞선 프레임의 피치와 스펙트럼을
  이어 붙여 빠진 프레임을 만들어낸다. 한 프레임이면 들리지 않는다. Reed-Solomon은 가끔 있는 손실을
  고치려고 매 프레임 대역폭을 쓴다.
- **한 프레임 = 한 패킷, 언제나.** 256 kbps에서 최대 **182바이트** (예산 1163). 오디오는 절대
  단편화하지 않고 재조립도 필요 없다.
- **오디오 콜백 경로에 락이 없다.** 지터 버퍼·디코더·채널 수신단이 전부 콜백 안에 있고 다른
  스레드는 보내기만 한다. 콜백은 OS가 정한 데드라인에서 도는데, 스케줄러가 재운 스레드가 쥔 락을
  기다리면 그게 바로 지터 버퍼가 막으려던 그 드롭아웃이다.
- **무음도 보낸다.** WASAPI 루프백은 기계가 조용하면 0을 주는 게 아니라 **아무것도 주지 않는다.**
  도착한 것만 인코딩하면 스트림이 멈추고, 소리가 나는 바로 그 순간 클라이언트 버퍼는 빈 상태에서
  채우기 시작한다.
- **SDL의 큐를 얕게 유지한다.** 거기 쌓인 건 지터 버퍼 위에 더해지는 지연이다. 이 세션의 깊이는
  측정에 근거한 버퍼의 결정이지, 독립적인 두 추측의 합이 아니다.

지터 버퍼 실측: 균일한 경로 **2프레임(10ms)**, 30ms씩 멈추는 경로 **7프레임**, 안정되면 다시 2로
복귀. 한 번의 스톨 때문에 낸 지연을 세션 내내 물고 있으면 사람이 몇 시간 동안 그걸 느낀다.

또 하나의 무의미한 통과를 잡았다: TS 디스패처가 채널 2에 대해 `'audio has no layout before M7'`을
던지고 있어서, 새 오디오 reject 벡터가 **엉뚱한 이유로** 통과했다. 예전 FEC 때와 같은 부류.
이번엔 Rust 디스패처의 `Ok(_) => false` 포괄 분기도 없앴으니, 채널 6이 생기면 조용히 통과하는 대신
컴파일 에러가 난다.

### Electron 셸: 터미널 없이 쓸 수 있는 형태로 (2026-09-07)

`packages/host`(트레이)와 `packages/client`(창). 둘 다 실제로 뜨고, 스크린샷으로 회귀를 잡을 수
있게 `PRISM_PANEL_SCREENSHOT` / `PRISM_WINDOW_SCREENSHOT` 경로를 남겼다.

**napi 표면이 노출하는 것 전부:** 신원 공개키, 페어링(코드 생성·호스트 대기·클라이언트 접속),
페어링된 기기 목록, 호스트 세션(시작·스냅샷·정지). 프레임도 패킷도 개인키도 이 경계를 넘지 않고,
넘을 수 있는 함수 자체가 없다. 스냅샷은 200ms 주기로만 밀고, 패널이 숨겨져 있으면 아예 보내지
않는다 — 아무도 안 보는 통계는 영상을 인코딩하는 바로 그 기계에서 하는 낭비다.

**스트림 창은 별도 프로세스다.** macOS에서 창은 메인 스레드에서 구동돼야 하는데 Electron이 이미
그 스레드를 쥐고 있어서, 이 프로세스 안의 스트림 창은 **존재할 수 없다.** 그 제약이 어차피 더 나은
배치로 밀어붙인다: 디코드·표시 경로가 Electron이 멈춰 세울 수 없는 곳에서 돌고, 인터페이스를
끌고 내려가지 않으면서 죽을 수 있으며, "프레임은 V8을 통과하지 않는다"가 규율이 아니라 구조로
성립한다. 클라이언트 창은 `prism-cli client --display`를 자식 프로세스로 띄우고 그 출력을 읽는다.

호스트 세션은 시작·감시·정지가 되는 서비스(`prism_core::control::host`)로 바뀌었다. CLI는 프레임
예산을 채우고 요약을 찍으면 끝이지만 애플리케이션은 그럴 수 없다 — 사람이 누르면 시작하고 몇 시간
돌다가 다시 누르면 멈춘다. `frames: Option<u32>`가 그 둘을 같은 코드로 덮는다.

부수적으로 `lint:cross`가 또 한 번 값을 했다: 캡처 루프가 없는 Linux에서 `note`/`keep_going`/
`Instant`가 dead code가 되어 `-D warnings`에 걸렸다. macOS에서만 빌드했다면 CI에서야 알았을 것.

### 랑데부 서버: NAT 뒤 두 지점을 만나게 한다 (2026-09-07)

`crates/prism-rendezvous`. UDP 소켓 하나와 해시맵 둘. **별도 STUN이 필요 없다** — 데이터그램을
받은 서버는 이미 출발지 주소를 알고 있고, 그게 STUN이 하는 전부다.

**서버는 아무것도 신뢰받지 않는다.** 세션 키를 보지도 만들지도 못한다. 적대적인 서버가 할 수 있는
최대치는 소개를 거부하거나 틀린 주소를 알려주는 것이고, 틀린 주소는 그냥 Noise 핸드셰이크에
실패한다. 그래서 싸구려 박스에 올려도 타협이 아니다.

**등록은 증명을 요구한다.** 호스트가 공개키를 주장하면 서버는 *그 키에 대한 DH*로 봉인한 챌린지를
보낸다. 개인키를 가진 쪽만 열 수 있다. 이게 없으면 호스트의 공개키를 본 적 있는 누구나 — 페어링한
모든 기계가 — 그 키로 등록해서 클라이언트를 딴 데로 보낼 수 있다. 읽지는 못해도 호스트는 도달
불가능해지고, 그게 공격의 전부다. 등록은 **등록된 주소에서 온 keepalive로만** 갱신된다.

**Docker 브리지 네트워킹은 이 서버를 조용히 망가뜨린다.** `-p 47500:47500/udp`로 띄우고 측정:

```
host registered ... reachable at 185.125.190.82:45762
client: the host is at 185.125.190.82:45762, and this machine appears at 185.125.190.82:20016
```

양쪽 다 서버와 같은 기계의 `127.0.0.1`에 있었다. 둘 다 존재하지 않는 주소를 향해 펀칭했고, 아무것도
연결되지 않았으며, **아무 에러도 나지 않았다** — 뚫리지 않는 NAT과 구분이 안 된다. `network_mode:
host`가 유일하게 성립하는 배치다. `deploy/rendezvous/compose.yaml`에 이 이유를 적어뒀다.

이미지는 **1.5 MB**. 정적 링크된 바이너리 하나에 셸도 패키지 매니저도 라이브러리도 없다. 의존성이
전부 순수 Rust이기 때문에 가능하다.

검증 (로컬, host 네트워킹):

```
host: registered with <server>, reachable at 127.0.0.1:55828
host: a client is calling from 127.0.0.1:50909
client: session established ... 150 frames reassembled, 0 packets unparseable
```

**아직 검증되지 않은 것: 실제 두 NAT 사이의 홀펀칭.** 프로토콜 로직과 브로커 경로는 확인됐지만,
붙어 있는 기계가 전부 같은 집 NAT 뒤(112.77.96.85)이거나 Tailscale 위라 진짜 통과 시험을 못 했다.
공인 주소를 가진 랑데부가 생기는 시점에 측정한다.

### 페어링과 방향 전환: 사람이 쓸 수 있는 형태로 (2026-09-07)

**6자리 코드가 SPAKE2를 필요로 하는 이유부터.** 6자리는 백만 가지고, 노트북은 백만 개를 1초
안에 시도한다. PIN의 해시를 와이어에 올리거나 PIN에서 직접 키를 유도하면 그 순간 오프라인
전수조사가 가능해지고, 비밀이 아니게 된다. SPAKE2는 추측을 **실제 호스트를 상대로만** 검증할
수 있게 만들고, 호스트는 **1번**만 허용한다. 백만 번을 왕복 1회씩, 첫 실패에서 멈추는 호스트를
상대로 — 그건 공격이 아니다.

교환은 3메시지(1.5 RTT). 별도의 키 확인 단계는 없다 — **봉인 자체가 확인**이다. 코드가 틀리면
키가 달라지고 봉인이 열리지 않으며, 거기서 끝난다. 어느 자리가 틀렸는지는 새어나가지 않는다.

측정으로 확인한 성질:

| 성질 | 왜 필요한가 |
|---|---|
| 코드는 성공·실패 무관하게 1회로 소진 | 2번을 허용하면 백만 번도 허용하는 것이다 |
| **길이가 틀린 메시지는 코드를 소진하지 않는다** | 아니면 정크 데이터그램 하나로 페어링 창을 태울 수 있다 |
| 방향마다 다른 키 | 두 봉인이 고정 논스를 쓰므로, 키를 공유하면 그대로 논스 재사용 |
| PIN은 `Debug`에 찍히지 않는다 | 로그·에러 리포트는 정확히 찍히면 안 되는 곳이다 |
| 자리마다 0~9가 모두 나온다 | 바이트를 10으로 나눈 나머지를 쓰면 낮은 자리가 편향돼 탐색 공간이 줄어든다 |

**그리고 토폴로지를 뒤집었다.** M1~M4에서는 호스트가 클라이언트로 걸었다. 측정에는 괜찮았지만
**인터넷에서는 성립하지 않는다** — 호스트는 클라이언트가 말을 걸기 전까지 그 주소를 알 방법이
없다. 지금까지 동작한 건 Tailscale 주소를 손으로 넘겼기 때문이다.

이제 호스트가 듣고 클라이언트가 건다. 부수적으로 Noise_IK의 역할과도 맞아떨어진다: 거는 쪽이
상대의 정적 키를 이미 아는 쪽이고, 그게 정확히 페어링이 클라이언트에게 준 것이다.

```
호스트:      prism-cli pair host              → 코드 표시, 대기
클라이언트:  prism-cli pair client --host <주소> --pin <코드>
그다음:      prism-cli host                   (키 인자 없음)
             prism-cli client --host <주소>   (키 인자 없음)
```

페어링한 뒤로는 양쪽 다 키를 타이핑하지 않는다. 호스트는 페어링된 클라이언트 중 **누가 걸어와도**
받는다 — 누가 걸지 미리 고를 수 없으니 그게 유일하게 가능한 동작이다. 페어링한 적이 없는 호스트는
아무도 받지 않는다.

### 세션 암호화: 평문 경로를 없앴다 (2026-09-07)

**인터넷을 평문으로 건너던 것을 멈추는 게 M5에서 가장 값어치 있는 일이었다.** 원격 데스크톱은
키 입력을 실어 나르고 입력 주입을 받아들이므로, 인증 없는 플로우는 *포트에 닿을 수 있는 누구나
호스트에 타이핑할 수 있는* 플로우다. 기밀성보다 인증이 먼저다.

구현된 것:

| 계층 | 내용 |
|---|---|
| `net/seal.rs` | ChaCha20-Poly1305 패킷 봉인, 8B 논스 카운터 + 64칸 리플레이 창 |
| `net/handshake.rs` | `Noise_IK_25519_ChaChaPoly_BLAKE2s`, 1-RTT, 재전송/중복을 견디는 드라이버 |
| `net/secure.rs` | 소켓 경계에서 봉인·개봉. **평문으로 보낼 수 있는 경로가 존재하지 않는다** |
| `prism-cli` | `keygen` 서브커맨드, `--identity` / `--peer-key`. 키 없이는 세션이 서지 않는다 |

설계에서 값을 치른 지점들:

- **논스 카운터는 원자적**이다. 호스트는 인코더 스레드에서 비디오를, 리턴 패스 스레드에서
  클럭 응답을 같은 방향·같은 키로 보낸다. 핸들마다 카운터를 따로 두면 둘 다 0에서 시작해
  모든 논스를 재사용하고, 그건 암호가 약해지는 게 아니라 인증 키가 새는 것이다.
- **태그를 검증한 뒤에 카운터를 판정한다.** 순서가 반대면 키 없이 카운터만 찍어 보낸 패킷 하나로
  리플레이 창을 2^63까지 밀어버릴 수 있고, 그 뒤 진짜 패킷은 전부 창 밖으로 떨어진다.
- **개봉 실패는 세션을 끝내지 않는다.** 실패를 호출자에게 에러로 올리면 수신 루프를 쓰는
  자연스러운 방법이 "첫 위조 패킷에서 세션 종료"가 된다 — 인터넷 어디서든 데이터그램 하나로
  세션을 죽일 수 있는 DoS.
- **핸드셰이크 메시지는 타입 바이트가 없다.** 인증 자체가 구분해 준다: 봉인된 패킷은 핸드셰이크
  메시지로 검증되지 않고, 그 반대도 마찬가지. 대신 응답이 유실된 경우를 위해, 답한 쪽은 첫 봉인
  패킷을 받을 때까지 같은 바이트로 다시 답할 준비를 유지한다.
- **거절은 침묵이다.** 페어링되지 않은 상대에게 거절 메시지를 보내면 스캔에게 "여기 살아 있는
  호스트가 있다"고 알려주는 셈이다.

**암호 선택은 측정으로 뒤집혔다.** 처음에 AES-256-GCM으로 썼는데, 순수 Rust `aes` 크레이트는
x86에서는 런타임에 AES-NI를 잡지만 **stable aarch64에서는 하드웨어 AES를 못 쓴다.** 클라이언트가
바로 그 aarch64 기계다.

| 암호 | 1176B 봉인+개봉 | 처리량 |
|---|---|---|
| AES-256-GCM | 10.9 us | 0.9 Gbps |
| **ChaCha20-Poly1305** | **3.7 us** | **2.5 Gbps** |

3배 차이. 와이어 포맷은 그대로다(논스 12B, 태그 16B 동일). WireGuard가 같은 이유로 같은 선택을
했다.

검증 (전 구간 암호화된 채로):

| 시나리오 | 결과 |
|---|---|
| 루프백 60fps 200프레임 | 200/200, 개봉 실패 0, 피드백 200/200 |
| 손실 5% + 패리티 20%, 1슬라이스 | **400/400**, 패리티로 336 슬라이스 복구 |
| 손실 5% + 패리티 20%, 4슬라이스 | 371/400 — 암호화 이전 기록과 동일 (블록 크기 문제이지 암호 문제가 아님) |
| 페어링 안 된 호스트 | 클라이언트가 침묵, 호스트는 10초 뒤 타임아웃 |
| 페어링 안 된 클라이언트 | 동일 |

부수적으로 고친 것: `snow`의 `std` 피처가 `ring/std`를 통해 옵셔널 C 의존성 `ring`을 켜서
`pnpm lint:cross`를 깨뜨렸다. 피처를 실제로 쓰는 프리미티브만 남겨 순수 Rust로 유지했다.
그리고 vitest가 `.claude/worktrees` 안의 낡은 트리 복사본 3개까지 돌리고 있었다 — 옛 와이어
포맷 테스트가 통과하면서 회귀를 가릴 수 있는 상태였고, 루트 `vitest.config.ts`로 제외했다.

### 미해결: 주기적 ~58ms 스톨

루프백 1080p60에서 p99를 망치는 스톨이 있다. 프레임레이트와 무관하게 크기가 같고(30fps·60fps 모두 max ~58ms),
fps가 높을수록 그 뒤에 걸리는 프레임이 많아져 p99가 나빠진다(30fps 26ms → 60fps 55ms).

배제한 원인:
- CPU 경합 — 18코어(P6+E12)에 두 프로세스 합쳐 10% 미만
- 수신 스레드 블로킹 — 스레드 분리로 도착 p99가 51.8ms → 5.2ms로 해결됨
- poll 타임아웃 만료 — 0회
- 디코더 출력 지연 — `outlag` 측정 결과 전 구간 0.00ms (넣은 프레임과 나온 사진이 항상 1:1)

남은 가설은 **한 머신에서 인코더와 디코더가 Apple Silicon 미디어 엔진을 공유하는 경합**이며,
M1의 실제 구성(Windows 호스트 → macOS 클라이언트)에서는 발생할 수 없다. **판정은 두 머신 구성에서 한다.**

### 크로스 머신 검증 (2026-09-06)

macOS ARM64 호스트 → Windows 11 ARM64 클라이언트(UTM VM), 실제 네트워크. 1080p60 H.264.

| 항목 | 결과 |
|---|---|
| 패킷 | 11,076 / 11,076 (후속 실행에서 2패킷 손실 관측) |
| 프레임 | 300 / 300 (손실 발생 시 미완성 1개만 폐기, 299개 정상) |
| 중복·오류 | 0 |

와이어 포맷과 재조립이 두 OS·두 아키텍처에서 동일하게 동작함을 확인했다. 손실 처리도 실전에서 검증됐다.

**이 검증이 계획을 하나 바꿨다.** 크로스 머신 지연이 `p50 0.00 p99 0.00 max 0.00 ms`로 나왔는데,
두 시계가 어긋나 뺄셈이 음수가 되고 `saturating_sub`가 0으로 뭉갠 결과였다. 완벽한 지연처럼 보이는 거짓 숫자였다.
이제 측정 불가를 명시적으로 보고한다. **M2의 클럭 동기화는 선택이 아니라 두 머신 측정의 전제 조건이다.**

### NVENC 슬라이싱·파라미터 세트 반복·실제 화면 캡처 (2026-09-07)

**실제 데스크톱이 2560×1440으로 인터넷을 건너갔다.** 400프레임 전부 재조립, 396 디코드, 실패 0,
전 구간 p50 22.68 / p99 29.06 ms. 다만 213초가 걸렸다(1.9 fps) — 원격 데스크톱이 유휴라
WGC가 줄 것이 없었던 것이지 경로 문제가 아니다.

**슬라이스 스트리밍이 켜졌다.** Apple Silicon이 `-12900`으로 거부하던 바로 그 기능이고,
NVENC에서는 `sliceMode=3`으로 프레임당 슬라이스 수를 지정하면 된다. 1080p60, 같은 비트레이트에서:

| 프레임당 슬라이스 | 전 구간 p50 | p99 |
|---|---|---|
| 1 | 15.67 ms | 21.50 ms |
| 4 | 16.07 ms | **17.89 ms** |

p50은 사실상 같고 p99가 개선된다. 수신 측은 여전히 프레임 전체를 기다리므로(sub-frame write 미적용)
얻는 것은 네트워크에 고르게 퍼지는 효과뿐이다. 진짜 지연 이득은 `enableSubFrameWrite`가 필요하다.

**파라미터 세트를 매 프레임 반복한다** (`repeatSPSPPS`). VideoToolbox 쪽에 손으로 넣었던 것과 같은 이유고,
NVENC에는 전용 비트가 있다.

**혼잡 제어 액추에이터는 아직 동작하지 않는다 — 측정으로 확인했다.**
`nvEncReconfigureEncoder`는 **성공을 반환하지만 출력 비트레이트가 따라오지 않는다.**

| | 요청 | 실측 |
|---|---|---|
| 초기화 시 고정 | 8 Mbps | 7.2 Mbps |
| 초기화 시 고정 | 40 Mbps | 34.8 Mbps |
| 20으로 시작 → 재구성으로 40 | 40 Mbps | **17 Mbps** (20 Mbps가 내는 값) |

재구성 156회 수락, 거부 0회. VBV 창을 건드리지 않아도 결과는 같았다.
`resetEncoder`가 빠진 것인지, 프리셋이 소유한 필드 때문인지, 이 드라이버 특유의 문제인지는 미확인이다.
**컨트롤러는 송신 페이서를 움직이고 페이서는 실제로 듣는다.** 인코더도 같은 숫자를 전달받지만 따르지 않고,
동작한다고 주장하는 것보다 안 된다고 적는 편이 낫다.

### M1 수직 슬라이스 완주 — 실제 인터넷 경로 (2026-09-07)

**Windows(GTX 1660) 호스트 → macOS 클라이언트, 실제 인터넷.** NVENC 인코딩 → UDP → VideoToolbox 디코드.
경로는 Tailscale 직결(`110.8.104.218:41641`, DERP 릴레이 아님), 왕복 9.17 ms.

| | 완성 / 600 | 전 구간 p50 | p99 | 실측 비트레이트 |
|---|---|---|---|---|
| 패리티 없음 | 598 | **16.11 ms** | **18.51 ms** | 16.9 Mbps |
| 패리티 20% | 596 | 15.89 ms | 17.79 ms | 20.6 Mbps |

1080p60에서 **M1 게이트(p99 < 40ms)를 절반 이하로 통과**한다. 이 숫자에는 왕복 9 ms가 들어 있으므로
파이프라인 자체는 약 9 ms다. 단계별로는 디코드 p50 2.03 / p99 2.89 ms, 도착 p50 13.86 ms.

이 실행에서 링크는 깨끗했다(600 중 2 손실). 그래서 FEC는 슬라이스 1개만 복구했다 — **손실이 없으면
FEC는 대역폭만 쓴다**는 당연한 사실의 실측이고, 적응형 패리티가 필요한 이유이기도 하다.

**이 테스트가 실제 버그를 하나 잡았다: 요청한 비트레이트가 무시되고 있었다.**
NVENC 프리셋 설정을 그대로 통과시켰더니 20 Mbps 요청에 **40.3 Mbps**가 나왔고 프레임 하나가 182 KB였다.
클라이언트가 못 따라가 디코더 큐가 넘쳤고, 프레임 하나가 버려지자 참조 사슬이 끊겨
**580프레임 연속 `kVTVideoDecoderBadDataErr`** — IDR이 하나뿐인 스트림은 영영 복구하지 못한다.

진단 순서가 중요했다. 같은 비트스트림을 (1) ffmpeg가 디코드했고 (2) macOS 디코더도 로컬에서 30/30
디코드했으며 (3) 클라이언트가 받은 프레임 바이트를 덤프해 호스트가 보낸 것과 크기까지 정확히 일치함을
확인했다. 그래서 남은 것은 처리량뿐이었다. 짧은 실행(5프레임)에서는 멀쩡했으므로 **긴 실행이 아니었다면
못 잡았을 결함**이다.

고친 내용: 프리셋이 채운 설정 위에 `rateControlMode = CBR`, `averageBitRate`, 그리고
**`vbvBufferSize`를 정확히 한 프레임치**로 덮어쓴다. 계획서가 지연 스파이크의 최대 원인으로 꼽은
바로 그 값이다. 오프셋은 손으로 세지 않고 컴파일러가 헤더에서 읽은 값을 썼다.

### NVENC 첫 인코딩 성공 (2026-09-07)

캡처 → GPU NV12 변환 → NVENC → Annex B 전 구간이 붙었다. GTX 1660, 1080p60, P1 프리셋.

| 항목 | 결과 |
|---|---|
| 인코딩 지연 | p50 **2.78 ms**, p95 3.59, p99 4.18, max 7.08 ms |
| 출력 | 120프레임 / 9.53 MB |
| 구조 | **I 1개 + P 119개, B-프레임 0** |

**검증은 자기 자신이 아니라 독립 디코더로 했다.** 비트스트림을 Mac으로 옮겨 ffprobe/ffmpeg로 확인:
H.264 High profile, 1920×1080, yuv420p, level 4.2, **120/120 프레임 전량 디코드**, 디코드한 프레임을
PNG로 뽑아 원본 패턴과 일치함을 눈으로도 확인했다. VideoToolbox 인코더 검증과 정확히 같은 방식이고
같은 결론(I 1개 + P 119개)이다.

**구조체 배치는 컴파일러에게 물었다.** `NV_ENC_INITIALIZE_PARAMS`를 손으로 계산했더니 1776이 나왔는데
실제는 **1800**이고 `tuningInfo` 오프셋도 112가 아니라 **136**이었다. 그대로 썼으면 실패가 아니라
메모리 손상이었다. 헤더를 clang으로 파싱해 크기와 오프셋을 뽑고, Rust 쪽에 컴파일 타임 단언을 걸어
어긋나면 빌드가 깨지게 했다 — 실제로 첫 시도에서 그 단언이 걸려 잡혔다.

**`NV_ENC_CONFIG`는 건드리지 않는다.** 4KB에 코덱별 union이 든 구조체이고, 이 코드가 안 쓰는 필드
하나하나가 틀릴 기회다. 드라이버에 프리셋을 요청해 그대로 넘긴다.

### NVENC 능력 실측: macOS가 거부한 것 전부를 지원한다 (2026-09-06)

빌린 Windows PC(GTX 1660, Turing, 드라이버 591.86, NVENC API 13.0)에서 실측.

| 능력 | H.264 | HEVC | 계획서 항목 |
|---|---|---|---|
| REF_PIC_INVALIDATION | ✅ | ✅ | 5번 LTR + 참조 무효화 |
| NUM_MAX_LTR_FRAMES | 8 | 7 | 〃 |
| INTRA_REFRESH | ✅ | ✅ | 4번 intra-refresh |
| DYNAMIC_SLICE_MODE | ✅ | ✅ | 2번 슬라이스 스트리밍 |
| ASYNC_ENCODE | ✅ | ✅ | 3번 async 인코드 |
| DYN_BITRATE_CHANGE | ✅ | ✅ | 11번 적응형 비트레이트 |
| 최대 해상도 | 4096 | 8192 | |

**macOS에서 불가능하다고 결론 낸 두 항목(LTR, intra-refresh)이 여기서는 전부 가능하다.**
슬라이스 제어도 마찬가지다 — Apple Silicon이 `-12900`으로 거부하던 바로 그것이다.

**그러나 계획서의 핵심 목표에 하드웨어 한계가 걸린다.** `MB_PER_SEC_MAX = 983,040`이고
매크로블록은 16×16이므로, 실측된 프레임레이트 천장은:

| 해상도 | H.264 천장 |
|---|---|
| 720p | 273 fps |
| 1080p | **120 fps** |
| 1440p | **68 fps** |

**이 GTX 1660으로는 M6의 1440p120이 불가능하다.** 1080p120은 정확히 딱 맞는다.
`NUM_ENCODER_ENGINES = 1`이고 상위 카드는 2~3개를 갖는다. 1440p120은 더 빠른 NVENC가 필요하다.
목표를 유지하려면 하드웨어 요구사항으로 명시해야 하고, 아니면 M6 목표를 1080p120으로 조정해야 한다.

**바인딩은 손으로 쓰고 DLL은 런타임에 로드한다.** 생성하려면 빌드 시점에 NVIDIA Video Codec SDK가
있어야 해서 macOS 크로스빌드와 모든 CI 러너가 깨진다. 링크하면 NVIDIA 없는 기계에서 실행 자체가 안 된다.
런타임 로드면 같은 바이너리가 어디서든 돌고, 인코더가 없으면 없다고 보고할 뿐이다.

**버전은 협상해야 한다.** 헤더는 13.1을 선언하는데 이 드라이버는 13.0을 구현하고,
13.1을 요구하자 `NV_ENC_ERR_INVALID_VERSION`으로 거부당했다. 드라이버에 먼저 묻고 그 값으로
모든 구조체를 찍는다.

### 실측: 실제 GPU에서의 캡처와 변환 (2026-09-06)

GTX 1660, 2560×1440 @ 60Hz 실제 디스플레이. VM(1 Hz)에서 못 재던 숫자다.

| 항목 | 결과 |
|---|---|
| 캡처 | 300프레임 / 5.78초 = **51.9 fps** |
| 프레임 간격 | p50 **16.67 ms** (60Hz 주기와 정확히 일치), p99 33.34 ms |
| BGRA→NV12 제출 | p50 **0.04 ms**, p99 0.13 ms |

p99가 정확히 두 주기라는 것은 가끔 한 프레임을 건너뛴다는 뜻이고, 화면이 그만큼 안 바뀐 것이다.
**변환 0.04 ms는 CPU가 작업을 제출하는 시간이지 GPU가 끝내는 시간이 아니다** — D3D11은 지연 제출이다.
병목이 CPU가 아니라는 것만 확인됐고, GPU 시간은 아직 안 쟀다.

### BGRA → NV12 색 변환 (D3D11) (2026-09-06)

WGC는 BGRA를 주고 모든 하드웨어 H.264 인코더는 NV12를 원한다. CPU에서 변환하면 GPU 메모리에서
프레임을 읽어내야 하고(1440p120에서 초당 400MB) 캡처 경로를 그렇게 만든 이유가 통째로 무너진다.
그래서 드로우 콜 두 번이다 — 루마 평면 전해상도, 크로마 평면 절반.

**검증은 자기 자신이 아니라 macOS 디코드 셰이더와 대조했다.** 두 셰이더는 반대 방향으로 독립적으로
작성됐고 같은 BT.709 video range 숫자에서 만나야 한다.

| 입력 RGB | 기대 Y'CbCr | 출처 |
|---|---|---|
| (255,255,255) | 235, 128, 128 | Metal 테스트가 흰색으로 디코드하는 바로 그 값 |
| (0,0,0) | 16, 128, 128 | 〃 검정 |
| (128,128,128) | 126, 128, 128 | 〃 회색 |
| (255,0,0) | 63, 102, 240 | BT.709 표준식에서 직접 계산 |
| (0,255,0) | 173, 42, 26 | 〃 |
| (0,0,255) | 32, 240, 118 | 〃 |

원색 세 개는 **BT.709과 BT.601을 가르는 지점**이라 넣었다. 계수를 잘못 쓰면 화면은 그럴듯하게
나오면서 색만 틀린다.

**선형화하지 않는다.** BT.709의 `Y'CbCr`은 감마 인코딩된 R'G'B' 위에 정의되고 캡처된 BGRA는
이미 감마 인코딩돼 있다. 선형 광으로 바꾸고 변환하는 것은 흔한 실수이며, 흑백을 제외한 모든 곳에서
틀린 그림을 만든다.

**크로마는 평균 내지 않고 샘플링한다.** 절반 해상도에서 bilinear 샘플러를 쓰면 출력 텍셀 하나가
아래 4개 텍셀의 평균이 되고, 그게 크로마 서브샘플링이 원하는 box 필터다. 행렬이 R'G'B'에 대해
선형이라 행렬 뒤에 평균 내는 것과 앞에 평균 내는 것이 같은 답을 준다.

**이 테스트는 대화형 데스크톱이 필요 없다** (D3D11 디바이스 생성만 필요). SSH로 돌아가므로 CI에서도 돈다.

### Windows 캡처 (WGC) 첫 동작 (2026-09-06)

Windows 11 amd64 VM(UTM, GPU 패스스루 없음)에서 `Windows.Graphics.Capture`가 동작한다.

| 항목 | 결과 |
|---|---|
| 세션 | 1280x800, D3D11 하드웨어 디바이스 생성 성공 |
| 텍스처 | `DXGI_FORMAT_B8G8R8A8_UNORM`, `D3D11_USAGE_DEFAULT` |
| 바인드 플래그 | `SHADER_RESOURCE \| RENDER_TARGET`, CPU 접근 플래그 0 |

바인드 플래그와 CPU 접근 0이 **제로카피 계약 그 자체다.** 인코더가 그대로 바인드할 수 있고
CPU가 읽을 수 없다는 것은 GPU가 사본을 만들지 않았다는 뜻이다.

**처리량은 이 VM에서 측정할 수 없다.** 39프레임/10초(3.9 fps)가 나왔고 화면을 계속 바꿔도 오르지 않는데,
원인은 코드가 아니다 — `Microsoft Basic Display Adapter`가 **`CurrentRefreshRate: 1`(1 Hz)**을 보고한다.
WGC는 화면이 바뀔 때만 프레임을 주고, 이 가상 디스플레이는 사실상 갱신되지 않는다.
**실측은 NVIDIA PC가 필요하다.** 그래서 테스트는 프레임레이트를 일절 단언하지 않는다 —
여기서 잰 숫자는 아무 의미가 없다.

`hardware=true`가 나온 것은 뜻밖이다. Basic Display Adapter인데도 `D3D_DRIVER_TYPE_HARDWARE`로
디바이스가 만들어졌다. WARP 폴백은 그래서 이번엔 쓰이지 않았지만, 없으면 언젠가 막힐 경로라 남겨둔다.

### 인코더: LTR은 안 되고, 진짜 문제는 다른 데 있었다 (2026-09-06)

**Apple Silicon 하드웨어 H.264 인코더는 `EnableLTR`을 거부한다.** 실제로 열어서 확인한 결과다
(`ltr_supported() == false`). `MaxH264SliceBytes`와 같은 전례이고, 헤더에 상수가 있다는 것이
실리콘이 구현했다는 뜻이 아님을 다시 확인시켜준다.

**따라서 계획서 M4 항목 5(LTR + 참조 무효화)는 macOS 호스트에서 불가능하다.** Windows/NVENC
호스트가 필요하고, 그건 아직 존재하지 않는다. 이 플랫폼의 손실 복구 답은 FEC이고,
5% 손실에서 399/400을 이미 달성했으므로 충분하다.

**계획서 M4 항목 4(intra-refresh)도 macOS에서 불가능하다.** 프로퍼티가 없다(84개 전부 확인).
그리고 없애려던 키프레임 스파이크는 여기 존재하지도 않았다 — `MaxKeyFrameInterval`이 100,000이라
IDR 하나 + 무한 P 스트림이다.

**대신 실제로 망가져 있던 것을 고쳤다.** VideoToolbox는 SPS/PPS를 IDR에만 붙여 내보내고
`strip_parameter_sets`가 나머지에서 제거하므로, **프레임 0 이후 파라미터 세트가 다시는 나가지 않았다.**
늦게 접속하거나 첫 프레임을 잃은 클라이언트는 영원히 검은 화면이고 어디에서도 오류가 나지 않는다
(`client.rs`가 `NoParameterSets`를 조용히 삼킨다). M5에서 클라이언트가 돌아가는 호스트에 붙는 순간
터질 문제였다.

이제 60프레임마다 파라미터 세트를 반복한다. 측정 결과 프레임 0, 60, 120에 실리고 **IDR은 여전히 0번뿐**이다.
키프레임 강제는 같은 효과를 내지만 초당 비트레이트 스파이크를 대가로 치른다 — 계획서가 없애려던 바로 그것이다.
파라미터 세트 두 개는 수십 바이트라 메가비트 스트림에서 사실상 공짜다.

**런타임 비트레이트 변경은 동작한다.** 양방향 모두. 이것이 혼잡 제어의 진짜 액추에이터이고,
이제 인코더 기반 두 호스트 경로가 모두 컨트롤러를 따른다.

### 송신 페이싱 + 혼잡 제어 (2026-09-06)

**페이싱은 루프백에서 순수 비용이다.** 막힐 병목이 없으니 프레임의 마지막 패킷만 늦출 뿐이다.

| | p50 | p99 |
|---|---|---|
| 페이싱 없음 | 0.33 ms | 0.97 ms |
| 고정 25 Mbps 페이싱 | 8.89 ms | 10.29 ms |

이 8.5ms는 페이싱의 본질적 대가이고, 값어치는 실제로 막히는 경로에서만 나온다.
루프백에서 페이싱을 튜닝하면 잘못 튜닝하게 된다 — ~58ms 스톨과 같은 교훈이다.

**페이싱만으로는 액추에이터가 아니다.** 소스가 계속 같은 양을 만들면 큐가 호스트 안으로 옮겨갈 뿐이다.
소스가 19.6 Mbps를 원하는데 페이서를 8 Mbps로 굶긴 실험:

| | p50 | p99 | 500프레임 소요 |
|---|---|---|---|
| 컨트롤러 없음 | 31.21 ms | 33.58 ms | **16.5s** (실시간의 2배) |
| 적응형 | 8.99 ms | 14.70 ms | **8.3s** (실시간) |

그래서 합성 소스도 컨트롤러를 따라 **생산량 자체를 줄인다** — 실제 인코더가 비트레이트 지시를 받는 것과 같다.
프레임 경로에 할당이 생기지 않도록 슬라이스를 다시 만들지 않고 앞부분만 잘라 보낸다.

**손실 기반 백오프는 혼잡이 아닌 손실 앞에서 무너진다. 그리고 FEC가 그것을 막는다.**

| | 컨트롤러 최종 | 완성 프레임 |
|---|---|---|
| 깨끗한 링크 | 51.2 Mbps | 500 / 500 |
| 5% 손실, 패리티 없음 | **1.0 Mbps (바닥)** | 246 / 500 |
| 5% 손실 + 패리티 20% | 51.0 Mbps | 497 / 500 |

주입된 손실은 비트레이트와 무관하므로 속도를 바닥까지 내려도 손실은 그대로다 — 화질만 버리고 아무것도 못 얻는다.
무선이나 policer가 있는 경로에서 실제로 일어나는 일이다.
FEC를 켜면 손실이 **프레임 손실이 되기 전에** 복구되어 컨트롤러 눈에 띄지 않고 속도가 유지된다.
**FEC는 복구 수단일 뿐 아니라, 혼잡 제어가 손실 많은 링크를 혼잡한 링크로 오해하지 않게 막아주는 장치이기도 하다.**

**지연 신호에는 호스트 자신의 페이싱 지연이 포함된다.** `capture_ts_us`는 페이싱 전에 찍히기 때문이다.
부호는 여전히 맞다 — 속도를 올리면 페이싱 지연이 줄고, 막힌 경로에서 속도를 올리면 큐 지연이 는다 —
하지만 깨끗한 링크에서 천장까지 더 빨리 올라가는 원인이 된다.

### FEC 결과: 84% 프레임 손실을 0.25%로 (2026-09-06)

같은 조건(루프백, 400프레임, 5% 패킷 손실, 시드 1)에 Reed-Solomon 패리티를 켠 결과.
프레임당 슬라이스 1개 — **Apple Silicon에서 `MaxH264SliceBytes`가 안 먹히므로 실제 인코더가 내는 형태**다.

| 패리티 | 완성 프레임 | 버려진 프레임 | 복구된 슬라이스 |
|---|---|---|---|
| 없음 | 62 / 400 | 337 | — |
| 10% | 383 / 400 | 17 | 315 |
| 15% | 396 / 400 | 4 | 325 |
| **20%** | **399 / 400** | **1** | 321 |

**블록 크기가 비율보다 중요하다.** 같은 20% 패리티라도 프레임을 4슬라이스로 쪼개면 371/400에 그친다.
9데이터+2패리티(11샤드) 블록은 코딩 효율이 나빠서 2개만 잃어도 못 살리기 때문이다.
36데이터+8패리티(44샤드)는 8개까지 버틴다 — 같은 대역폭으로 훨씬 강하다.
슬라이스를 잘게 쪼개는 것은 지연에는 좋지만 **복구력에는 정확히 반대로 작용한다.**
이 트레이드오프는 실제 인코더에서는 나타나지 않는다. 슬라이스 제어가 애초에 안 되기 때문이다.

**`tail_len`이 조용한 손상을 막는다.** 재조립기는 슬라이스의 실제 길이를 **마지막 패킷에서만** 배운다
(`reassemble.rs`). 그 패킷을 FEC로 복구하면 길이가 0으로 남아 디코더에 빈 비트스트림이 넘어가고
어디에서도 오류가 나지 않는다. 그래서 패리티 패킷이 마지막 데이터 샤드의 길이를 나른다 —
나머지는 전부 정확히 1180이므로 이것 하나로 참 길이가 복원된다.

**패리티도 똑같이 버린다.** 손실 주입기가 패리티 패킷을 면제하면 실제 경로보다 복구가 좋아 보인다.
실제 경로에서는 수리 수단도 수리 대상만큼 잃어버린다.

### VAAPI: Intel GPU에서 H.264가 나왔다, 그리고 하드웨어가 설계를 하나 뒤집었다 (2026-09-07)

Linux 호스트의 인코더를 실제 하드웨어(msi, Intel TigerLake UHD, iHD 26.1.2, VA-API 1.23)에서
세웠다. ffmpeg가 결과를 읽는다:

```
codec_name=h264   profile=High   width=1920   height=1080   pix_fmt=yuv420p   level=41
```

1080은 67.5매크로블록이라 68로 코딩하고 크롭해서 되돌린다. 그게 맞게 나왔다는 것이 SPS의
크롭 필드가 옳다는 증거다.

**드라이버에 물어서 알게 된 것 셋. 블라인드로 썼으면 전부 틀렸다.**

| | |
|---|---|
| `EncSlice` 엔트리포인트 | **없다.** `EncSliceLP`(저전력)만 있다. 모든 예제가 쓰는 일반 경로로 가면 `UNSUPPORTED_ENTRYPOINT`로 시작조차 못 한다 |
| AV1 인코드 | **없다.** 프로파일 32가 목록에 없다. 코드가 번호를 안다고 광고하면 안 되고 드라이버에 물어야 한다 |
| 레이트 컨트롤 | **`VA_RC_CQP`만.** CBR이 없다 |

**세 번째가 설계 결정 1번을 무효화한다.** VideoToolbox과 NVENC은 목표 비트레이트와 1프레임
VBV를 받지만, 여기는 요청할 대상 자체가 없다. 유일한 레버는 양자화 계수(QP)이고, 비트레이트를
지키려면 그것을 프레임마다 움직여야 한다 — 프레임이 예산을 넘으면 한 단계 거칠게, 밑돌면 한
단계 곱게, 근처면 그대로. 한 번에 한 단계인 이유는 갑자기 바뀐 화면 하나에 여러 단계를 뛰면
그 프레임보다 **뒤따르는 못난 프레임들이 더 눈에 띄기** 때문이다. QP는 18~42로 묶었다. 51은
합법이지만 볼 수 없는 그림이고, 거기까지 가야 하는 상황이면 목표를 낮추는 것이 혼잡 제어의
일이지 이쪽 일이 아니다.

**파라미터 세트도 직접 써야 한다.** `VAConfigAttribEncPackedHeaders`가 0x1f — 드라이버가
SPS/PPS를 써주지 않는다. 비트 단위로 쓰는 코드를 `encode::h264`에 넣었고, GPU가 필요 없는
순수 문법이라 모든 플랫폼에서 테스트한다 (표준의 Exp-Golomb 표를 그대로 대조한다).

**같은 사실을 두 번 말해야 하고 아무도 대조해주지 않는다.** 한 번은 하드웨어를 위해
`VAEncSequenceParameterBufferH264`에, 한 번은 디코더를 위해 비트스트림에. 둘이 어긋나면
인코더는 만족하고 디코더는 쓰레기를 읽으며 어디에서도 오류가 안 난다. 그래서 하나의 `Sps`
기술에서 양쪽을 만든다.

**VUI를 끝까지 안 써서 한 번 걸렸다.** `nal_hrd_parameters_present_flag` 뒤에 세 필드가 더
있는데 거기서 멈췄더니, 디코더가 정지 비트와 패딩을 그 필드로 읽고 `cpb_count 33 invalid`를
냈다. 위치로 읽는 문법에서 일찍 멈추는 것은 값을 틀리게 쓰는 것과 같다.

### Windows 호스트 경로도 같은 파이프라인 위로 (2026-09-07)

macOS에서 찾은 두 결함이 Windows 경로에 그대로 있었다. 따로 쓰였고 아무도 나란히 놓고 보지
않았기 때문이다.

- **키프레임 요청 미처리** — `frames == 0`이 유일한 IDR. 즉 **Windows 호스트도 손실 복구가
  통째로 없었다.** 프레임 하나만 잃으면 영원히 검은 화면
- **정상 종료를 실패로 보고** — 클라이언트를 닫을 때마다 트레이에 에러

`encode::pump`을 플랫폼 모듈로 바꿔서 `ScreenPump`이라는 **한 이름이 컴파일된 쪽을 가리키게**
했다. 그래서 `control::host::stream`이 이제 플랫폼당 하나가 아니라 **전체에 하나**다. 남은
플랫폼별 코드는 "프레임을 어떻게 잡고 어떻게 인코딩하는가"뿐이고, 그게 실제로 다른 유일한
것이다.

**Windows에서 파이프라이닝은 하지 않았다.** NVENC 래퍼가 동기라 겹칠 것이 없다. NVENC 자체는
`enableEncodeAsync`와 완료 이벤트를 갖고 있고 — 계획의 설계 결정 3번이 바로 그것이다 —
macOS에서 66 → 197 fps였던 만큼의 값어치가 있을 것이다. 다만 **하드웨어를 앞에 두고 써야 할
코드**이고, 기계에 접근이 없다.

**M8의 나머지는 하드웨어가 막고 있다.** AMF 심과 oneVPL은 SDK 헤더가 필요하고, Linux 호스트와
Windows/Linux 클라이언트는 그 기계가 필요하다. 실행해 본 적 없는 인코더 백엔드를 쓰는 것은
이 저장소가 일하는 방식의 정반대다.

### M9 달성: macOS 호스트, 그리고 조용히 실패하는 권한 (2026-09-07)

Mac이 완전한 호스트가 됐다. 한 세션에서 전부 확인:

| | |
|---|---|
| 캡처 | ScreenCaptureKit 1920×1080 60 fps |
| 인코드 | HEVC, 클라이언트가 **240/240 디코드** |
| 오디오 | 시스템 오디오, 평균 82바이트 Opus |
| 입력 주입 | `injection confirmed` — 6500+ 이벤트, wire p50 0.04 ms / p99 0.08 ms |

**권한 안내 흐름이 M9의 진짜 내용이다.** macOS의 두 권한은 거부돼도 실패하지 않는다.
Screen Recording 없이 캡처하면 스트림이 열리고 정시에 프레임을 주는데 전부 검은색이다
(오디오는 전부 침묵). Accessibility 없이 주입하면 이벤트를 보내고 성공을 보고하는데 아무 데도
가지 않는다. **어디에서도 오류가 나지 않으므로, 묻지 않은 호스트는 동작하는 것처럼 보이고
동작하지 않는다.**

이번 세션에서 오디오가 조용히 0을 내는 것을 네 번 오진하며 하루를 쓴 것이 정확히 이
성질 때문이다. 그래서 묻는 일은 세션 중이 아니라 세션 전에, 사람이 볼 수 있는 곳에서 한다.

- `control::permissions` — 프롬프트 없이 상태를 보고. 인터페이스가 다시 그려질 때마다
  불러도 되고, 그리는 것이 사람 앞에 시스템 대화상자를 띄울 이유는 아니다
- 제어를 끈 호스트에게는 Accessibility를 묻지 않는다. 주지 않겠다고 한 사람 대신 그 기계의
  제어권을 요구하는 셈이 된다
- **요청과 허가는 다르다.** 시스템은 한 번만 묻는다. 그 뒤로는 같은 거절을 영원히 돌려주고
  아무것도 보여주지 않는다 — 결정이 설정으로 옮겨갔고 거기서는 사람만 바꿀 수 있기 때문이다.
  그래서 거절을 받으면 해당 설정 창을 여는 것이 유일한 길이고, 코어는 링크만 돌려준다
  (프로세스를 띄우는 것은 앱의 일)
- `prism-cli permissions` — 헤드리스에서도 같은 답. 부족하면 0이 아닌 종료 코드

### M7 달성: 소리가 와이어를 건넜다 — 막고 있던 것은 내 플래그 한 줄이었다 (2026-09-07)

**게이트 (루프백, 10초, 손실 없음):**

| | |
|---|---|
| 호스트 | 오디오 2028프레임(10.1초) + 영상 600프레임 |
| 클라이언트 | 영상 **600/600 디코드**, 오디오 **2027프레임 평균 82바이트**, 166.9 kB |

A/V 둘 다 10초 내내 끊김 없이. 평균 82바이트가 핵심이다 — 128 kbps × 5 ms = 80바이트이고,
**침묵은 5바이트**다.

**진단을 네 번 틀렸다.** 캡처는 정시에 버퍼를 주는데 전부 0이었고, 나는 차례로 바이너리별
TCC, Screen Recording 미허가, `Drop`이 `replayd`를 망가뜨림, 블루투스 출력 라우팅을
의심했다. 전부 아니었다.

범인은 `setExcludesCurrentProcessAudio(true)` — **내가 넣은 한 줄이다.** 무해해 보였다.
호스트는 자기 소리를 내지 않으니 배제할 자기 소리도 없어야 한다. 그런데 여기서 말하는
"current process"는 이 실행 파일이 아니라 **책임 프로세스**, 즉 실행 체인 꼭대기의
애플리케이션이다. 같은 곳에서 시작된 것은 전부 같이 배제된다.

플래그만 뒤집고 다른 것은 하나도 바꾸지 않은 측정:

| `excludesCurrentProcessAudio` | peak | Opus 평균 |
|---|---|---|
| `true` | **정확히 0** | 5바이트 |
| `false` | 3.613e-2 (-28.8 dBFS) | **82바이트** |

원격 데스크톱은 기계가 내는 소리를 보내려고 존재하는데, 이 플래그는 그중 일부가 해당 없다고
조용히 결정한다. 껐다. 대가는 호스트와 클라이언트를 한 기계에서 돌릴 때의 피드백 루프인데,
클라이언트가 별도 프로세스라 이 플래그가 애초에 막아주지도 못했다.

**진단이 왜 그렇게 오래 걸렸는가가 이 항목의 요점이다.** 이 실패의 모든 원인이 똑같은
증상을 낸다: 정시에 도착하는 빈 버퍼. 그리고 **5바이트 Opus 프레임은 침묵의 올바른
인코딩**이라 어디에서도 오류가 나지 않는다. 샘플 값을 직접 재는 것이 원인들을 가르는 유일한
지점이고, 그래서 `prism-cli audio` 프로브가 있다. 호스트도 10초간 무음이면 한 번 말한다.

### 긴 슬라이스는 FEC 밖에 있었다 — 하필 키프레임이 (2026-09-07)

Reed-Solomon 블록은 전부 합쳐 255샤드다. 그보다 긴 슬라이스는 블록 하나로 못 덮어서
**보호 없이 나갔다.** 하필 그게 키프레임이다: Apple Silicon 인코더는 슬라이스 크기 제한을
무시하고 프레임 통째로 넘기므로, 실제 비트레이트에서 키프레임은 수백 패킷이 된다.
**절대 잃으면 안 되는 프레임 하나가 정확히 보호에서 빠져 있었다.**

같은 명령, 같은 시드 (합성 400 KB 1슬라이스 = 347패킷, 3% 손실, 20% 패리티):

| | 이전 | 이후 |
|---|---|---|
| 호스트 | `slice of 347 packets … sending it unprotected` | 경고 없음 |
| 완성 프레임 | **0 / 300** | **250 / 250** |
| 유실 프레임 | 296 | **0** |
| 패리티 복구 | — | 494 슬라이스 |

**와이어 포맷은 안 건드렸다.** 처음에는 패리티 헤더에 블록 인덱스가 필요해 보였는데,
`FEC_HEADER_LEN`은 `VIDEO_HEADER_LEN`과 같아야 한다 — 패리티 샤드는 자기가 고치는 데이터
샤드와 정확히 같은 길이여야 하고, 헤더가 한 바이트만 커져도 패킷이 MTU를 넘는다. 여유 바이트가
없다.

그런데 리어셈블러는 프레임을 **슬라이스를 순서대로 이어붙여** 만든다. 그래서 긴 슬라이스를
여러 와이어 슬라이스로 쪼개면 수신 측에는 완전히 투명하다. 헤더 몇 개 값 외에는 비용도 없다.
와이어 슬라이스 번호는 이제 호출자가 아니라 발신 측이 매긴다 — 인코더의 슬라이스 하나가
와이어에서 여럿이 될 수 있고, 언제 그런지는 발신 측만 안다.

**이 표는 손실 내성 숫자 전체가 어디에 걸려 있었는지도 보여준다.** 기존 M4 게이트는 40 KB
프레임(4슬라이스 36패킷)으로 측정해서 한계 근처에 간 적이 없었다. 슬라이스가 212패킷을 넘는
순간 FEC가 조용히 꺼지고, 그 사실을 말해주는 것은 한 번 찍히는 경고문 한 줄뿐이었다.

### Electron 셸로 실제 세션을 열었다 — 그리고 앱만으로는 접속이 불가능했다 (2026-09-07)

트레이의 "Start hosting"을 눌러 세션이 열리고, 클라이언트 창의 Connect를 눌러 **368프레임이
앱에서 앱으로 흘렀다.** M5의 "UI에서 페어링→접속"이 처음으로 검증됐다.

| | |
|---|---|
| 호스트 패널 | Not hosting → Waiting for a client → **Streaming** → Not hosting, 368프레임, error `null` |
| 클라이언트 창 | **Streaming — 6e7248…e50105**, error `null` |

**구동 훅(`PRISM_PANEL_DRIVE` / `PRISM_WINDOW_DRIVE`)을 붙여서 확인했다.** 스크린샷 훅이
"창이 어떻게 생겼는지"를 말한다면 이건 "창이 뭔가 하기는 하는지"를 말한다. 스크립트는
렌더러 안에서 돌기 때문에 사람과 정확히 같은 경로 — 마크업의 버튼과 preload가 노출한 표면 —
로만 앱에 닿는다. 다른 방법으로 연 세션은 네이티브가 동작한다는 것만 증명하고 그 위의
애플리케이션에 대해서는 아무것도 증명하지 못한다.

**그런데 앱만으로는 애초에 접속이 불가능했다.** 양쪽에 짝이 되는 결함이 있었다.

- **호스트가 임의 포트에 바인드했다.** 기본값이 `0.0.0.0:0`이라 OS가 포트를 골랐고, 패널은
  그 포트를 표시하지 않았고, 바꿀 설정도 없었다. 랑데부 없이 LAN에서 쓰면 클라이언트가
  알 방법이 없다. CLI 기본값(`47200`)에 맞추고, **실제 바인드된 주소를 패널에 표시**한다.
- **클라이언트에 호스트 주소를 입력할 곳이 없었다.** Connect가 주소로 빈 문자열을 보내서
  랑데부가 반드시 필요했다. 호스트별 주소 입력란을 넣고 설정에 기억시킨다.

**`0.0.0.0`을 보여주는 것은 사실이지만 쓸모가 없다** — 클라이언트가 접속할 수 없는 유일한
주소다. 인터페이스를 나열하는 대신 라우팅 테이블에 묻는다: UDP 소켓을 connect하면 아무것도
보내지 않고 커널이 경로를, 따라서 소스 주소를 고르게 만든다. 목적지는 절대 라우팅되지 않는
문서용 주소라 이 기계 밖으로 나가는 것은 없다. 인터페이스가 여러 개인 기계에서 맞는 것을
고르는데, 나열로는 할 수 없는 일이다.

**아직 안 고친 것:** 24 Mbps / 60 fps에서 호스트가
`slice of 361 packets is too large for one parity block (limit 231), sending it unprotected`
을 찍는다. 프레임당 1슬라이스인 Apple Silicon 인코더에서 키프레임이 231샤드 한계를 넘어
**FEC 보호를 못 받는다.** 가장 잃으면 안 되는 프레임이 정확히 보호에서 빠진다. 큰 슬라이스를
여러 패리티 블록으로 쪼개야 한다.

### 앱 경로를 처음 검증했더니 M6 수정이 하나도 없었다 (2026-09-07)

`prism-cli`와 Electron 앱은 **서로 다른 코드로 스트리밍한다.** CLI는 `host::run_captured`,
앱은 napi → `control::host::stream`. 여기에 Windows 분기와 CLI의 합성·NVENC 모드까지
"캡처 → 인코드 → 송신" 루프가 **다섯 벌**로 자라 있었다.

napi 경로를 Node에서 직접 띄워 처음으로 종단간 확인했다 (300/300 재조립·디코드). 그리고
그 경로에 **M6에서 만든 것이 둘 다 빠져 있었다**:

- 파이프라이닝 없음 → 1440p에서 CLI가 120 fps일 때 앱은 85 fps
- 키프레임 요청 처리 없음 → `frames == 0`이 유일한 IDR. **앱에서는 프레임 하나만 잃어도
  영원히 검은 화면.** 손실 복구가 통째로 없었다

각 사본은 따로 보면 멀쩡해서 아무것도 이 사실을 말해주지 않았다. 릴레이 폴백이 CLI에만
없던 때와 정확히 같은 표류다. `encode::pump::ScreenPump`로 단일화하고 두 호출자가 같은
파이프라인을 쓰게 했다.

**그 김에 앱 표면 버그 두 개가 드러났다.** 헤드리스로 세션을 돌려 숫자를 세기 전에는
둘 다 보이지 않던 것들이다.

1. **정상 종료가 실패로 보고됐다.** 연결된 UDP 소켓은 상대가 사라지면 다음 쓰기에서
   `ConnectionRefused`를 받는다(ICMP port unreachable). 이걸 에러로 처리해서, 클라이언트를
   닫을 때마다 트레이에 `Connection refused (os error 61)`가 떴다 — 즉 **거의 모든 세션이
   끝날 때마다**. 이제 `Pumped::PeerGone`으로 구분해 `stopped`로 끝난다.
2. **동의하지 않은 오디오를 보냈다.** CLI는 `agreed.audio`를 확인했지만 napi 경로는 안 했다.
   클라이언트가 "audio off"로 합의해놓고 초당 200프레임을 받아서 버리고 있었다. 검사를
   `spawn_audio` 안으로 옮겨 두 호출자가 같이 받게 했다.

### M6 달성: 1440p120 p99 18.5 ms — 병목은 인코더가 아니라 파이프라이닝이었다 (2026-09-07)

1440p120을 처음 돌렸을 때 호스트가 **85 fps밖에 못 냈다.** 600프레임에 7.09초.
인코더가 느린 줄 알았는데, 인코드 프로브만 따로 돌려보니 CPU 시간이 600프레임에 1.45초뿐이었다.
**계산하는 게 아니라 기다리고 있었다.**

원인은 호출부였다. `encoder.encode()`는 제출만 하고 즉시 반환하고 결과는 `poll()`로 오는데,
호스트 루프가 `encode(); poll();`로 붙여 써서 **항상 한 프레임만 인코더 안에 있었다.**
그래서 달성 프레임률이 `paint + encode_latency`의 **합**이 된다.

프로브에 `--in-flight`를 붙여 측정한 결과 (1440p HEVC, 600프레임):

| 동시 처리 | 소요 | fps | 지연 p50 | p99 |
|---|---|---|---|---|
| 1 | 9.05 s | 66 | 6.14 ms | 15.24 ms |
| **2** | **3.05 s** | **197** | **6.17 ms** | 17.52 ms |
| 3 | 2.96 s | 203 | 9.97 ms | 25.23 ms |
| 4 | 2.37 s | 253 | 13.54 ms | 24.02 ms |
| 6 | 2.34 s | 256 | 21.15 ms | 21.41 ms |

**2에서 처리량이 3배가 되는데 지연은 그대로다** (6.14 → 6.17 ms). 3부터는 겹치는 게 아니라
인코더 안에 **줄을 서는** 것이라 지연이 오른다 — 1프레임 VBV(설계 결정 1번)가 거부하려는 바로 그
거래다. 그래서 호스트는 2로 고정했다.

순서도 중요했다. `paint N; submit N; drain N-1`은 이미 인코드가 끝난 N-1을 아무 상관 없는
paint 뒤에 세워둔다. `submit N; drain N-1; paint N+1`로 바꾸면 완성된 프레임이 즉시 나간다.
버퍼는 프레임당 하나씩 필요하다 — 인코더가 아직 읽고 있는 버퍼에 그리면 **실패하지 않고**
아무도 그리지 않은 그림이 나간다.

**결과 (루프백, HEVC, 3000프레임, 패리티 10%):**

| | 이전 | 이후 |
|---|---|---|
| 실제 프레임률 | 85 fps | **120.0 fps** (25.00초에 3000프레임) |
| 재조립 / 디코드 | — | **3000 / 3000**, 실패 0 |
| 파이프라인 p50 | 7.31 ms | 12.55 ms |
| **파이프라인 p99** | 31.24 ms (85 fps에서) | **18.50 ms** |

**M6 목표 p99 < 25 ms를 통과했다.** 단 세 가지를 분명히 해둔다.
(1) 루프백이라 실제 네트워크 RTT가 빠져 있다.
(2) `pipeline`은 capture_ts → 디코드 완료이고 **표시(vblank) 대기가 빠져 있다** —
지연 예산표의 0~8.3 ms가 여기 더해져야 glass-to-glass가 된다.
(3) 합성 패턴 소스이고, 실제 화면 캡처는 ScreenCaptureKit 자체 지연 때문에 min이 20 ms에서 시작한다.

**NVENC 쪽도 같은 문제가 있을 것이다.** `run_windows`는 여전히 `encoder.encode()`가 동기로
프레임을 돌려주는 구조다. 로드맵의 "NVENC async encode"가 정확히 이 항목이고, Windows 기계에
접근할 수 있을 때 같은 측정을 반복해야 한다.

### 키프레임 요청: 제한 간격을 측정으로 정했다 (2026-09-07)

intra-refresh도 LTR도 macOS에서 못 쓰므로 프레임 하나를 놓치면 **그 뒤 전부가 영구히 디코드
불가**다. 모든 프레임이 참조 프레임이고 키프레임 주기가 사실상 무한이기 때문이다. 클라이언트가
스스로 고칠 방법은 없다. 그래서 피드백 패킷에 `FEEDBACK_WANTS_KEYFRAME` 1비트를 추가하고
(17 → 18바이트), 호스트가 다음 프레임을 IDR로 낸다.

간격을 얼마로 둘지는 **추측이 아니라 측정으로** 정했다. 720p60 6 Mbps, 손실 2%, 패리티 없음,
300프레임 5초:

| 제한 간격 | 요청 | 발급 | 디코드 성공 | 실제 대역 |
|---|---|---|---|---|
| 무제한 | 42 | 42 | 72% | 6.3 Mbps |
| 16 ms | 41 | 41 | 71% | 6.3 Mbps |
| **33 ms** | 46 | **42** | **70%** | **6.1 Mbps** |
| 50 ms | 49 | 40 | 68% | 6.3 Mbps |
| 100 ms | 125 | 37 | 53% | 6.3 Mbps |
| 250 ms | 176 | 19 | 28% | 6.2 Mbps |

**"키프레임은 비트레이트 스파이크"라는 전제가 이 인코더에서는 틀렸다.** 어느 간격에서도 실제
대역이 6.1~6.3 Mbps로 움직이지 않는다. CBR + 1프레임 VBV(설계 결정 1번)이므로 키프레임은
*더 큰* 프레임이 아니라 *같은 크기의 더 나쁜* 프레임이다. 길게 잡을 이유가 없고, 길게 잡으면
그림만 잃는다 — 250 ms는 28%다.

**그러면 제한은 왜 두는가.** 대역을 지키려는 게 아니다. 클라이언트는 못 디코드할 때만 요청하고
키프레임 하나가 밀린 요청 전부를 해소하므로 요청 수는 이미 스스로 억제된다 (깨진 프레임 56개에
키프레임 42개). 제한이 막는 것은 **그 규약을 안 지키는 피어**다. 매 리포트마다 비트를 세우면
제한이 없을 경우 호스트의 모든 프레임이 intra가 되고, 되돌아오는 1비트로 화질을 무너뜨릴 수 있다.

**패리티가 켜져 있으면 이 경로는 아예 발동하지 않는다.** 같은 조건에 패리티 20%를 켜면
300/300 디코드, 요청 0건, 파리티로 56슬라이스 복구. 키프레임 요청은 FEC가 못 고친 것만
받아내는 **최후 수단**이지 1차 방어선이 아니다.

### M4 기준선: 손실 없는 복구는 이렇게 무너진다 (2026-09-06)

피드백 루프와 결정론적 손실 주입기를 붙이고 측정한 **복구 수단이 하나도 없는 상태의 기준선**.
루프백, 합성 소스 400프레임, 40KB/frame 4슬라이스(프레임당 36패킷), 시드 1.

| 패킷 손실 | 완성된 프레임 | 버려진 프레임 |
|---|---|---|
| 0% | 300 / 300 | 0 |
| **5%** (실측 4.94%) | **62 / 400** | **337** |

**패킷 5% 손실이 프레임 84% 손실이 된다.** 프레임 하나가 36패킷이므로 `1 - 0.95³⁶ = 84.2%`,
이론값과 정확히 일치한다. 이 배율이 M4의 모든 숫자를 지배한다 —
혼잡 제어의 손실 임계값을 문헌에서 그대로 가져오면 **한 자릿수 이상 틀린다** (문헌은 패킷 기준).

FEC가 고쳐야 할 숫자가 이것이고, 시드가 있으니 실패한 실행은 그대로 재현된다.

**손실 주입은 OS 트래픽 셰이퍼가 아니라 인프로세스로 넣었다.** dummynet/clumsy/netem은 실제 소켓
경로를 지나가지만 관리자 권한이 필요하고 세 OS가 전부 다르며 CI에서 못 돈다. 인프로세스 드롭은
커널 경로를 시험하지 못하는 대신 결정론적이고 시드가 있으며 매 커밋마다 돈다. 후자가 회귀 테스트가
될 수 있는 유일한 쪽이다.

### 클라이언트 커서 렌더링 (2026-09-06)

호스트가 캡처에서 커서를 빼고(`show_cursor: false`) 위치만 제어 채널로 보내면, 클라이언트가 직접 그린다.
핵심은 **호스트 보고를 기다리지 않는다**는 것. 클라이언트는 자기가 보낸 움직임을 아는 유일한 쪽이므로
즉시 적용해서 그리고, 호스트 보고는 **보정**으로만 쓴다 — 호스트 쪽 사용자, 포인터를 옮기는 창, 화면 끝 클램프처럼
클라이언트가 알 수 없던 것들이 거기 담긴다.

보정은 표준 reconciliation이다. 보고에는 그것이 찍힌 호스트 시각이 들어 있고 클라이언트도 같은 시계로
입력을 찍으므로, 그 시각보다 오래된 움직임은 버리고 최신 것들을 보고 위에 다시 얹는다.
**재적용을 빠뜨리면 보고가 올 때마다 커서가 왕복 시간만큼 뒤로 튄다.**

검증: 실제 포인터를 3440x1440 화면 정중앙(0.500, 0.500)에 고정하고 스크린샷 → 클라이언트 영상의
정중앙에 커서가 그려졌다. 좌표 매핑이 끝까지 맞는다는 뜻.

**이 과정에서 기존 버그를 하나 찾았다.** HUD 뒤 어두운 패널이 처음부터 한 번도 그려진 적이 없었다.
`CGContextSetFillColor`는 **컨텍스트의 현재 색공간**으로 성분 배열을 읽는데, 새 비트맵 컨텍스트의
기본 색공간이 그것이 아니어서 RGBA 4개가 회색+알파로 읽혀 알파 0이 됐다. 읽어낸 픽셀은 `rgba [0,0,0,0]`.
색공간을 스스로 들고 다니는 `CGColor`로 바꿔 고쳤고, 커서와 HUD 양쪽에 픽셀을 되읽는 회귀 테스트를 붙였다.
눈으로는 "글씨가 좀 안 보이네" 정도로만 보이던 종류의 결함이다.

### 크로스 머신 입력 검증 (2026-09-06)

Windows 11 amd64 호스트(UTM VM, 브리지 네트워크) ← macOS 클라이언트. 합성 프레임 900장 + 1000Hz 합성 입력.

| 항목 | p50 | p99 | 비고 |
|---|---|---|---|
| 비디오 도착 (Win → Mac) | 1.41 ms | 2.82 ms | 900/900 프레임, 32,400 패킷 손실 0 |
| 입력 와이어 (Mac → Win) | 0.53 ms | 0.79 ms | 11,000 이벤트 주입, `SendInput` 확인됨 |
| 클럭 동기화 | — | — | 오프셋 -818.76 ms, 최소 왕복 0.48 ms (60 샘플) |

`SendInput` 주입은 대화형 데스크톱에서만 동작한다. SSH 세션에는 주입할 데스크톱이 없어
Win32 오류 5(액세스 거부)로 거절되며, 테스트는 이를 실패가 아니라 건너뜀으로 처리한다.
CI에서 돌릴 수 있는 것은 스캔코드 테이블 테스트 9개이고, 포인터가 실제로 움직이는지는
예약 작업(`schtasks /it`)으로 대화형 세션에서 확인했다.

**입력 와이어 지연이 실행 중 0.35 ms → 0.53 ms로 단조 증가했다.** 큐 적체가 아니라 시계 드리프트로 읽는다.
15초에 0.18 ms면 12 ppm으로, VM 시계에서 흔한 값이다. 클럭 동기화는 최소 왕복 샘플 하나를 잡고
갱신하지 않으므로 세션이 길어질수록 그 샘플이 낡는다. **장시간 세션에서는 오프셋 재추정이 필요하다 — M4에서 다룬다.**

**두 머신 테스트에서 발견한 함정:** 호스트 소켓은 `--peer` 주소로 `connect()`되므로,
클라이언트가 **다른 인터페이스로 나가면** 커널이 조용히 버린다. 오류도 로그도 없다.
이 Mac은 같은 서브넷에 Wi-Fi와 이더넷이 둘 다 있어서, 클라이언트가 도달 가능한 주소가 아니라
**라우팅이 선택한 주소**를 `--peer`에 줘야 한다 (`route get <호스트>`로 확인). 비디오는 클라이언트 소켓이
연결되지 않아 멀쩡히 흐르는데 되돌아오는 경로만 죽으므로, 증상이 "입력만 안 되는" 것으로 나타난다.
M5의 ICE는 후보 쌍을 제대로 다루므로 이 문제가 사라진다.

빌드 경로: Mac에서 `cargo xwin build --target aarch64-pc-windows-msvc`로 10.9초 만에 크로스 빌드된다.
Windows 타깃에는 C 의존성이 없다(SDL3와 코덱이 모두 macOS 게이트).

- 전송 계층은 1440p120 목표 레이트에서도 예산의 1% 미만을 쓴다. 최적화 우선순위가 아니다.
- 120fps에서 max 8.17ms는 정확히 한 프레임 주기라 프로세스 스케줄링 지연으로 읽힌다. M2 표시 페이싱에서 다룬다.
- 인코더 출력은 ffmpeg으로 교차 검증했다: High profile 1080p, 120프레임 전량 디코드, I 1개 + P 119개(B-프레임 0).

## 계측 (M1부터 필수, 나중에 붙이면 늦다)

프레임마다 전 구간 타임스탬프를 찍는다:
`capture_start → capture_done → encode_submit → first_slice_out → encode_done → first_byte_sent → last_byte_sent → first_pkt_recv → frame_complete → decode_submit → decode_done → present_queued → present_done`

클럭 동기화로 호스트/클라이언트 타임스탬프를 비교 가능하게 만들고, 클라이언트에 Moonlight 스타일 통계 HUD를 오버레이한다. **모든 마일스톤의 통과 기준은 이 HUD의 p99 숫자로 판정한다.**

## 알아둘 제약과 비용

- **"간단한 설치"의 실제 비용은 코드서명이다.** macOS는 Apple Developer($99/년) + 노타리제이션, Windows는 OV/EV 코드서명 인증서(연 $100~400)가 있어야 경고창 없는 설치가 된다. 없으면 Gatekeeper/SmartScreen 경고를 사용자가 뚫어야 하고 "간단한 설치" 목표가 무너진다. M10 전에 미리 발급받아 둘 것.
- **Electron 설치 파일은 150~250MB.** 원클릭이긴 하지만 가볍지는 않다. 나중에 Tauri로 셸만 교체하면 10~15MB가 되고 코어는 그대로다 — 셸이 얇게 유지되도록 napi 표면을 작게 잡는 게 그 선택지를 열어둔다.
- **macOS 호스트는 TCC 권한 3종**(화면 기록 / 손쉬운 사용 / 입력 모니터링)을 요구한다. 온보딩 UX에서 가장 마찰이 큰 지점.
- **게임패드 주입은 v1에서 Windows(ViGEmBus, 드라이버 설치 필요)와 Linux(uinput)만.** macOS는 가상 게임패드 API가 없어 DriverKit 드라이버를 직접 써야 하므로 범위 밖.
- **macOS 호스트에서 LTR과 intra-refresh는 불가능하다.** 계획서가 M4에 넣었던 두 항목이며, 파라미터는 전부 NVENC의 것이다. VideoToolbox에 intra-refresh 프로퍼티는 존재하지 않고(`kVTCompressionPropertyKey_*` 84개 전수 확인), `EnableLTR`은 존재하지만 **Apple Silicon 하드웨어 인코더가 거부한다**(실측 `ltr_supported() == false`). `MaxH264SliceBytes`가 `-12900`을 뱉는 것과 같은 부류다. 이 플랫폼의 손실 복구는 FEC이고, 참조 기반 복구가 필요하면 NVENC 경로가 필요하다.
- **AV1 인코딩은 하드웨어 게이트**(NVIDIA Ada+ / AMD RDNA3+ / Intel Arc+). 반드시 협상하고 H.264로 폴백.
- **HEVC는 상용 배포 시 라이선스 이슈**가 있다. 개인/오픈소스면 무관하나 상용화 계획이 있으면 확인 필요.
- **Apple Silicon 인코더는 슬라이스 크기 제한을 지원하지 않는다.** 위 지연 항목 2 참조. macOS 호스트 한정 제약이며 Windows/NVENC에는 영향이 없다.
- **네이티브 SDK 직접**을 택했으므로 인코더 5종 × 디코더 4종을 각각 구현해야 한다. M8이 가장 무거운 단계이며, 여기서 일정이 밀릴 가능성이 가장 크다. 리스크가 크면 M8을 "NVENC + VideoToolbox만"으로 잠시 좁히고 나머지를 M10 이후로 미루는 것이 가장 안전한 조정 지점이다.
- **GPU 핸들·SDK 호출은 전부 `unsafe`.** Rust의 소유권이 FFI 너머까지 보호해주지는 않는다. 각 SDK 래퍼를 안전한 타입으로 감싸는 얇은 계층(`encode/nvenc.rs` 안에서만 `unsafe`)을 두고 나머지 코드는 safe로 유지한다.

## 검증 방법

- **단계별 지연:** 클라이언트 통계 HUD의 p50/p99 (M2부터 상시 가동). 각 마일스톤 통과 판정의 기준.
- **클릭→광자:** 호스트 화면에 색이 바뀌는 테스트 패턴을 띄우고, 클라이언트에서 클릭 → 240fps 카메라(스마트폰 슬로우모션으로 충분)로 클라이언트 화면 촬영 → 프레임 카운트. M3, M6에서 실측.
- **손실 내성:** `dummynet`(macOS) / `clumsy`(Windows) / `tc netem`(Linux)으로 손실 1/3/5%, 지터 5/20ms를 주입해 M4 통과 판정.
- **NAT 조합:** 서로 다른 회선(집 Wi-Fi + 휴대폰 테더링)으로 M5 검증. UPnP가 있는 공유기와 없는 공유기 양쪽에서 직결률을 재고, 대칭 NAT 강제 시 릴레이 폴백 동작 확인.
- **프로토콜 회귀:** `packages/protocol`의 테스트 벡터를 `cargo test`와 `vitest` 양쪽에서 돌려 Rust·TS 구현이 동일 결과를 내는지 CI 검증.
- **`prism-cli` 회귀:** 헤드리스 host↔client를 CI에서 루프백으로 띄워 패킷 손실 주입 시나리오를 자동화.
- **장시간 안정성:** 실제 게임 2시간 연속 세션에서 메모리 누수·지연 드리프트·오디오 싱크 이탈 없음 확인.

## 첫 커밋에서 할 일 (M0)

1. `rustup` 설치 (stable), `git init`
